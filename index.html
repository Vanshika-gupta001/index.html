PROBLEM

Before any real analysis can happen, someone has to manually check a dataset for missing values, duplicates, and general data health — a slow, repeatable step.

SYSTEM

A FastAPI backend (routes/upload.py) orchestrates profiling, anomaly detection, health scoring, insight generation, chart rendering, and PDF export in a single request. The Next.js/React frontend renders the results across a health card, gauge, dataset card, recommendation card, and chart gallery.

AI LAYER

A rule-based service (ai_summary.py / business_ai.py) turns the computed stats into a written summary and an executive-style business report. A separate service (chat_ai.py) integrates Google's Gemini API (gemini-2.0-flash) for open-ended dataset Q&A — implemented, though not yet wired into the live chat endpoint (see Engineering Log).

DECISIONS

The health score starts at 100 and subtracts 2 points per missing value and 5 points per duplicate row, floored at 0, then maps to a status (Excellent / Good / Needs Cleaning / Poor) and a letter grade (A+ to F). Duplicates were weighted higher because they directly distort aggregations, counts, and downstream analysis, while missing values are often manageable depending on their proportion and which column they hit.

RESULT

Produces a health score + letter grade, an anomaly report, an AI-generated summary and business report, charts, and a downloadable PDF from a single upload — replacing what would otherwise be manual review. Tested on CSV datasets with a mix of numeric and categorical columns; the engine successfully generated profiling metrics, data-quality indicators, and automated insights across them.

04 / APPROACH

How I think

A working scenario, and the sequence I'd actually walk through.

SCENARIO
"A messy business dataset arrives."

Before any model or dashboard is useful, the data has to be trustworthy. This is the same sequence behind the AI Business Analytics Platform's profiling engine.

01Understand the business question

Start from what decision the data needs to support — not the dataset itself.

02Inspect the data

Profile the dataset for structure, completeness, and health before touching analysis.

03Identify quality issues

Flag missing values and duplicate records — the exact step automated in the profiling engine.

04Establish a baseline

Defined quality bands using a weighted scoring approach: 80–100 = Good, 60–79 = Needs Attention, below 60 = Poor. These are an interpretable starting baseline rather than a claimed industry standard, meant to be calibrated as more datasets are evaluated.

05Select an approach

Chose the Z-score method for initial outlier detection — simple, computationally efficient, and interpretable for roughly normally-distributed numeric data. Would reach for IQR or Isolation Forest instead when data is heavily skewed or non-Gaussian.

06Validate

Tested the profiling engine on datasets where row counts, column types, missing values, duplicates, and summary stats could be checked by hand, and compared its output against direct pandas calculations to confirm the reported metrics were consistent.

07Communicate the insight

On CampaignOS, this meant translating a technical system into an "Agency CFO" business narrative for a pitch.

08Build a usable output

Ship it as an API and/or interface someone else can act on — not just a notebook.

04B / ENGINEERING LOG

Decisions, honestly logged

Real decisions and real incidents from building both projects — sourced from the repos, not invented after the fact.

WHY FASTAPI FOR AI BUSINESS ANALYTICS?

CONTEXT

Backend for the data-profiling engine and API layer of the AI Business Analytics Platform.

TRADEOFF

The project is API-first — it needs to expose profiling functionality as lightweight HTTP endpoints. FastAPI gives automatic OpenAPI/Swagger docs, Pydantic validation, type hints, and strong performance with little boilerplate. Django would have added unnecessary framework overhead for this service; Flask would've needed more manual setup for validation and API docs.

WHY NEXT.JS FOR CAMPAIGNOS?

CONTEXT

The Next.js/FastAPI architecture was built by the team's lead architect; my role on that stack decision was downstream — designing the UX and dashboard flows the frontend needed to support, not the framework choice itself.

TRADEOFF

The reasoning behind it: a dashboard-style analytics product benefits from a structured React framework, reusable components, TypeScript, and scalable architecture, and it integrates cleanly with an API-driven backend like FastAPI. Architecturally, the goal was to keep the analytics engine and API independent from the presentation layer so each could evolve separately.

WHAT BROKE?

INCIDENT

The AI Business Analytics project was originally kept in a folder on the Desktop. It ran fine at first — but broke once new pieces were added (an AI chatbot integration and some ML conditions), due to path/environment conflicts caused by the nested Desktop folder location.

LESSON

Moved the project to the root of the C: drive, which resolved the conflicts and got it running again — folder location and path setup can silently break a project as it grows.

WHY A THIRD DESIGN ITERATION?

CONTEXT

Leading product/UI-UX design for CampaignOS's dashboard.

DECISION

The first two design attempts didn't feel right, so a third version was designed from scratch.

OUTCOME

The third attempt was the one both my teammates and I were happy with — it became the version the team built on.

WHAT WOULD CHANGE AT SCALE?

CONSIDERATION

The project's own README lists this honestly as unfinished: rate limiting on /upload and /chat so one user can't hammer the pipeline, a background job queue (Celery/RQ) since profiling + charts + PDF + summary currently all run synchronously in one request, stricter file-size/CSV validation, and object storage (S3-compatible) instead of local disk once deployed somewhere without persistent disk.

SECRETS IN THE REPO

INCIDENT

An earlier version of the project's .env.example had a real Groq API key committed to it.

LESSON

The README now leads with a rotation step — revoke the old key and generate a fresh one before doing anything else — as a standing reminder before anyone else clones the repo.
